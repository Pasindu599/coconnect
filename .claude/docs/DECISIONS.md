## ADR-001: Firebase as the backend (2026-10-02)
> **Superseded by ADR-014 (2026-10-04):** the backend is Supabase now.
**Decision:** Use Firebase: Auth (phone OTP), Firestore, Storage, Cloud Functions.
**Why:** The SDK and config already exist in the app, so it needs the least rework within 2 weeks.
**Consequences:** Business rules move from `store.ts` into Firestore security rules and Cloud Functions. Use the Emulator Suite for local development and tests. Money ledgers in Firestore must be append-only and Functions-only.

## ADR-002: PayHere for payments, with platform-held escrow (2026-10-02)
**Decision:** Owners pay through PayHere into the platform's merchant account. The platform holds the funds until completion is confirmed, then pays out. In the MVP, payouts are bank transfers recorded by an admin.
**Why:** A Sri Lankan gateway, already referenced in the prototype.
**Consequences:** The checkout hash and webhook verification run in Cloud Functions; the merchant secret is never in the client. A `PaymentProvider` interface keeps the gateway swappable. **Open question:** confirm with PayHere and a business advisor that holding third-party funds is allowed before going live.

## ADR-003: Construction gets its own roles (2026-10-02)
**Decision:** Each category defines its own roles. Construction uses client, contractor, subcontractor and worker. Coconut keeps owner, broker (supervisor) and worker.
**Why:** Construction has a different hierarchy than coconut harvesting.
**Consequences:** Roles map onto shared capabilities (`poster`, `bidder`, `crew`) so the job engine stays generic. A user can hold different roles in different categories (`memberships: [{category, role}]`). In the MVP, a subcontractor bids directly to clients like a contractor; contractor-hires-subcontractor comes later.

## ADR-004: Shared Claude context is committed to git (2026-10-02)
**Decision:** Root `CLAUDE.md` plus `.claude/docs/` hold the plan, architecture, issues and decisions, and are committed.
**Why:** Claude Code loads `CLAUDE.md` automatically for every teammate, so all three sessions share the same context. Personal Claude memory is not shared.
**Consequences:** Updating these docs is part of finishing a task. `.claude/settings.local.json` stays personal and is not committed.

## ADR-005: Client-side keys are restricted, never hidden (2026-10-02)
**Decision:** Any key shipped to the browser (`VITE_*`, the Firebase web config) is treated as public. It is secured by provider-side restrictions — HTTP referrer + API allowlist + quota caps — and by one key per environment, not by keeping it out of the bundle. Secrets that must stay secret (the PayHere merchant secret, service accounts) never get a `VITE_` prefix and live only in Cloud Functions config.
**Why:** Vite inlines `VITE_*` at build time, so "hiding" such a key is not achievable and pretending otherwise leads to unrestricted keys. The leaked Maps key (KNOWN_ISSUES #2) was unrestricted, which made it a billing liability.
**Consequences:** No fallback keys in source — a missing key degrades to a visible "not configured" state rather than falling back to a shared one. `.env.example` holds placeholders only. Rotation steps live in [`runbooks/google-maps-key.md`](runbooks/google-maps-key.md). CI gets a secret scan with 2C-1. The Firebase web API key in `firebase-applet-config.json` is public by design and is **not** rotated; Firestore/Storage rules are what protect that data.

## ADR-006: Rules read authorization from custom claims; denormalize job parties onto sub-documents (2026-10-03)
> **Superseded by ADR-014 (2026-10-04):** RLS reads memberships and `is_admin` straight from the `users` table (always current, no claims, no token refresh). The denormalized `owner_id`/`supervisor_id` columns stay: they keep policies to a plain column check.
**Decision:** Firestore rules check `request.auth.token.memberships` (a custom claim mirrored by the `addMembership` Function) rather than `get()`-ing the caller's own `users/{uid}` doc on every rule evaluation. Documents that belong to a job but aren't the job itself (`attendance_days`, `attendance_entries`, `completions`, `disputes`) carry denormalized `owner_id`/`bidder_id` fields copied from the job/award at creation time, the same pattern already used for `owner_name` on jobs. Also: `users/{uid}` reads are restricted to the user themself and admins, not "any authenticated user" as first drafted in `data-model.md` — nothing in the UI needs a stranger's full profile, and the doc carries NIC numbers and phone.
**Why:** Firestore rules can `get()` one document by a known path cheaply, but can't run a query (e.g. "find the award for this job") — so any rule that needs to know "is this caller a party to this job" either reads a custom claim (free) or needs the relevant IDs already sitting on the document being evaluated. Rules tests (`tests/rules/`, S1-04) confirmed both approaches work; claims + denormalization was simpler and cheaper than threading extra `get()` chains through every rule.
**Consequences:** Every Function that creates one of these sub-documents (or that calls `addMembership`) must keep the claim and the denormalized fields in sync with their source of truth — a stale claim after a role change, or a stale `owner_id` after... (jobs don't change owners, so this is low-risk in practice). `src/lib/auth.ts` force-refreshes the ID token after `addMembership` so the client never acts on a stale claim.

## ADR-008: Guard every field access in `list`-reachable rules with `'field' in data` (2026-10-03)
> **Superseded by ADR-014 (2026-10-04):** Postgres has no missing-field problem; columns always exist.
**Decision:** Every `read` rule on a collection that any repository subscribes to with a bare `onSnapshot(collection(...))` (i.e. every collection in `firestore.rules` except nothing — they all are) checks field presence first: `fieldIs(resource.data, 'owner_id', uid)` instead of `resource.data.owner_id == uid`, and cross-document checks go through `refFieldIs()`, which also `exists()`-checks the referenced doc before `get()`-ing it.
**Why:** Firestore evaluates a `list`/collection-`onSnapshot` query's rule once per **candidate** document, and throws `permission-denied` with "Property X is undefined" the moment *any* candidate lacks a field the rule unconditionally accesses — even documents that would fail the rule anyway, and even when every document this app actually writes always has that field. `tests/rules/` (mostly single-document `get`/`set`) never caught this; `tests/integration/`'s real `onSnapshot` listeners did, on `isAdmin()` first (a non-admin token has no `admin` claim at all) and then on `awards.supervisor_id` the moment a second, differently-shaped document existed in the same collection during a test run.
**Consequences:** Every *new* collection or rule added after this point must use `fieldIs`/`fieldIn` (or the same guard pattern) for anything reachable via `read`, not `request.resource.data.x == y` style direct access — that style stays fine for `create`/`update`, which are always evaluated against one concrete, real document, never a list scan. Worth a standing note for whoever writes the next rule.

## ADR-009: Per-user collections need a `where`-scoped query, not a bare collection listener; denormalize what the query needs (2026-10-03)
> **Superseded by ADR-014 (2026-10-04):** under RLS a `select` returns only the visible rows instead of rejecting the query, so plain table listeners are safe.
**Decision:** `src/lib/data/firestoreSync.ts` adds `subscribeToOwnedCollection(name, uid, {ownerField, supervisorField}, ...)` (an `or(where(ownerField,'==',uid), where(supervisorField,'==',uid))` query) and `subscribeToDocument(name, id, ...)` (a single-document listener) alongside the existing bare `subscribeToCollection`. `bids`, `awards`, `payments`, `ledger`, `attendance_days`, `attendance_entries`, `completions` use the first; `users` uses the second. `estates`, `jobs`, `workers`, `ratings` keep the bare collection listener — their read rule is `isSignedIn()` only, with no per-document branch. `Bid` and `Award` each gained a denormalized `owner_id` (they already had `supervisor_id`) so their read rule is two plain field checks, satisfiable by the query above, instead of a cross-document `get()`.
**Why:** discovered empirically, the hard way, while writing `tests/integration/awardBid.test.ts`: Firestore evaluates a `list`/`onSnapshot`-on-a-collection query's rule once per **candidate** document and, if it can't prove the rule holds for the query *as issued*, denies the **entire** query — it does not fall back to filtering the result down to whatever the caller may see. A bare `collection(db,'bids')` listener can never be proven safe for a sealed-bid rule (some other bidder's doc always exists that fails it), so the whole listener got `permission-denied`, silently, for every caller except an admin reading a collection whose rule happens not to vary per document. The fix has to live on both sides at once: the *query* must be at least as restrictive as the *rule*, which for a two-sided (owner-or-supervisor) access pattern means the field the rule checks has to actually be a field on the document the query can filter on — hence denormalizing `owner_id`, not just picking a cleverer rule.
**Consequences:** Any future collection added to `store.startSync()` needs this same design decision made up front — "is this collection's read rule the same for every document (bare listener is fine) or does it vary per document (needs a scoped query, and the rule's check fields need to actually be queryable, i.e. present on the document)?" `tests/integration/` is the only test layer that catches a violation of this; `tests/rules/` (single-document get/set) structurally cannot, so a new sync path should get an integration test, not just a rules test, before being trusted.

An admin's own read, though, IS safe as a blanket unfiltered query — `isAdmin()` doesn't depend on `resource.data`, so it's the same true/false for every document regardless of query shape. `src/lib/data/reconciliation.ts` (S1-12) relies on this and it's verified in `tests/integration/reconciliation.test.ts`.

## ADR-012: `award.escrow_amount` is overwritten to the real charged total once a payment succeeds (2026-10-03)
**Decision:** `awardBid` sets `escrow_amount = bid.price` as a provisional value (no payment exists yet, so the platform fee isn't known). `payhereNotify`'s success transaction overwrites it to `payment.amount` — the actual total charged (bid price + platform fee) — at the same time it writes the `hold` ledger entry. `recordPayout`'s `release` ledger entry uses this same full total, and the fee itself never gets its own ledger line; it's implicit in `award.payout_amount` (new field) being smaller than `escrow_amount`.
**Why:** Found while building S1-12's reconciliation helper: the helper's invariant (`sum(hold) == sum(release)+sum(refund)+stillHeld`) can only balance if the `hold` entry and `escrow_amount` agree on what "the amount" means. They didn't — one included the fee, the other never had it. Rather than inventing a separate `fee`-type ledger entry to make a split-amount scheme balance (which the existing `ledger.type` enum would technically support), the simpler fix was to make `escrow_amount` mean one consistent thing throughout the award's life: the full amount actually sitting in PayHere's custody, available from the moment a real payment exists.
**Consequences:** Anything reading `award.escrow_amount` before a payment succeeds sees a provisional (bid-price-only) estimate, not the final figure — fine for display ("≈ this much"), not fine for anything that needs the authoritative number, which should wait for `escrow_status != 'pending'`. `Award` gained `payout_amount` so an admin UI can show "released LKR X, of which LKR Y went to the platform fee" without a `ledger` join.

## ADR-010: Every Cloud Function must use the named Firestore database, not `getFirestore()`'s `(default)` (2026-10-03)
> **Superseded by ADR-014 (2026-10-04):** there is one Postgres database; no named-database trap.
**Decision:** `functions/src/db.ts` exports `getDb()` (and the `DATABASE_ID` constant for tests), which calls `getFirestore(DATABASE_ID)`. Every Function uses this, never a bare `getFirestore()`.
**Why:** `firebase-applet-config.json` (the AI-Studio-provisioned project this app already uses — see S1-03) sets `firestoreDatabaseId` to a **named** database, and `src/lib/firebase.ts`'s client `db` export passes that id to `getFirestore(app, firestoreDatabaseId)`. `getFirestore()` with no arguments — what every Function used until this point — defaults to the separate `(default)` database. The two had been silently writing to and reading from different databases since S1-05: `onUserCreate`, `addMembership`, `setAdmin` and (within this same pass) `awardBid` all wrote to `(default)`, which the actual client app never reads from at all. Caught via `tests/integration/awardBid.test.ts`: a real HTTP call to `awardBid` succeeded, wrote exactly the document asked for, and a plain client-side `getDocs()` of the "same" collection *right after* still returned zero results — not a permission or timing issue, a different database entirely. Every earlier manual/automated check had — by chance — only ever exercised one side or the other (rules tests and the S1-05 REST verification both defaulted to `(default)`; S1-07's sync test never crossed from Function-written data back through a client read).
**Consequences:** This was a complete backend/frontend disconnect for every already-shipped Function — real users would never have seen their own `onUserCreate`-created profile, and `addMembership` would have silently done nothing from the app's point of view. Fixed now, before S2 wires any UI to these paths, which is the only reason it didn't become a production incident. `scripts/seed.ts` had the identical bug (`getFirestore(app)`, no database id) and is fixed in the same pass, now importing `DATABASE_ID` from `functions/src/db.ts` rather than keeping a second hardcoded copy. Any future Admin SDK script or Function must do the same.

## ADR-011: Platform fee is 5% flat, stored in `config/platform`, Functions-only (2026-10-03)
> **Updated by ADR-014:** now the `platform_config` table (`key = 'fee_percent'`), read by `create_payment_intent()`; no client grant.
**Decision:** The platform fee is 5% of `bidPrice`, no tiers, for the MVP. It lives in a Firestore doc `config/platform` (`{ fee_percent: 5 }`), read by `createPayment` at call time (not cached across cold starts — the config doc is tiny and barely read, so the extra read per call is cheap next to the win of being adjustable without a redeploy). No collection rule grants it to clients — it falls through to `firestore.rules`' deny-all catch-all, same posture as `awards`.
**Why:** `payments.md` flagged this as the one open value in an otherwise-frozen `FeeBreakdown` shape (CONTRACTS C4). 5% is a reasonable, round MVP default; nothing in the current spec or roadmap calls for tiers, and adding them now would be solving a problem nobody has yet.
**Consequences:** Changing the fee later is a Firestore write to one doc (by an admin tool or directly in the console), not a deploy. `scripts/seed.ts` seeds `config/platform` so the emulator has a usable value out of the box. If tiered or category-specific fees are ever needed, `config/platform` can grow fields without breaking `createPayment`'s read of `fee_percent`.

## ADR-013: `/security-review` on the full S1 diff found and fixed two broken-access-control bugs; a third (`workers` PII) needs S2 (2026-10-03)
**Decision:** Ran `/security-review` against the complete `2c9fbcf..HEAD` diff (everything built in S1), independently verified each candidate finding with a second confidence pass before touching code. Two confirmed, high-confidence (9/10) findings were fixed in this same pass:
1. **`bids`:** a bidder could self-accept/reject their own bid (the update rule's bidder branch placed no restriction on the new `status` value) and could forge `owner_id` on create (the job `get()` only checked `status == 'OPEN'`, never ownership) to hide a bid from its real owner or leak it elsewhere. Fixed with `unchanged('status')` on the bidder branch and an `owner_id` equality check against the job doc on create.
2. **`completions`:** anyone could create a completion doc naming an arbitrary victim job/owner (only `submitted_by`/`status` were checked), making it appear in that owner's confirm-completion feed; `confirmCompletion.ts` never verified the submitter was the real awarded supervisor. Fixed two ways: `awardBid` now denormalizes `supervisor_id` onto the job doc so the `completions` create rule can `get()`-check both `owner_id` and `submitted_by` against it, and `confirmCompletion.ts` independently re-checks both against the award record before advancing escrow, as defense in depth in case a rule gap is ever reintroduced.

A third finding — `workers`' read rule (`isSignedIn()` only) lets any authenticated user read every worker's NIC number and bank account reference platform-wide — was **not** fixed unilaterally and is tracked as KNOWN_ISSUES #29 / a CONTRACTS.md change request to S2 instead.
**Why:** The first two were pure `firestore.rules`/Functions fixes within S1's ownership, verifiable end-to-end by the existing four test layers, so fixing them immediately (rather than just reporting them) matched the session's "run to 100%" mandate. The third is different in kind: a correct fix requires either a data-model split (`Worker` public fields vs. a `supervisor_id`/admin-only private doc) that touches several S2-owned component files, or a change to `BidsModal.tsx`'s/`AttendanceTab.tsx`'s own query pattern — both outside S1's file ownership and both risk conflicting with S2's concurrent work if changed unilaterally. A fourth candidate finding (a theoretical race between a client write to `users/{uid}` and the async `onUserCreate` trigger forging `nic_status`) was investigated and **rejected**: `onUserCreate`'s `.set(..., {merge:true})` names `nic_status` explicitly, so it unconditionally overwrites any forged value back to `'unverified'` on every run regardless of race order, and nothing in the codebase actually gates a real privilege on `nic_status` (posting/bidding/payouts all key off membership custom claims) — a self-healing, sub-second window with no lasting exploitable effect, not a concrete issue.
**Consequences:** All four test layers (310 unit, 57 rules, 58 Functions, 8 integration) plus `tsc --noEmit` and the Functions build pass with both fixes applied; two new rules tests were added (`tests/rules/firestore.test.ts`: self-accept, owner_id forgery, completions forgery) as regression coverage. `scripts/seed.ts`'s awarded demo jobs (`job-102`, `job-103`, `job-c102`) now also carry `supervisor_id` so they stay valid completion targets under the tightened rule. KNOWN_ISSUES #29 and the new CONTRACTS.md row are the handoff for the one remaining open item; nothing about the fix requires S2 input, but the remaining gap does.

## ADR-007: Keep existing collection/field names (`estates`, `supervisor_id`, ...) for every category, don't generalize them now (2026-10-03)
**Decision:** `data-model.md`'s first draft proposed renaming `estates` → `sites` and `Bid`/`Worker`/`Award`'s `supervisor_*` fields → `bidder_id`/`manager_id`, to read better for non-coconut categories. S1-07 reverses that: the Firestore collection stays `estates`, and `supervisor_id`/`supervisor_name`/`supervisor_phone`/`supervisor_trust_score`/`supervisor_fee` stay as-is, for construction bids/workers/awards too.
**Why:** Those field names are the existing `Estate`/`LabourJob`/`Bid`/`Worker`/`Award` types in `src/types/index.ts`, read by roughly 100 call sites across `src/components/**` — Session 2's files, which this session does not edit and which a second, concurrently-running Claude Code session was actively working in while this was being built. CONTRACTS.md's C2 explicitly allows S1 to change a store signature "if S1 updates every caller in the same PR, with an S2 reviewer" — neither was available here, so the safe default is: don't rename. The mistake was caught before anything merged built on top of the wrong names (S1-04's first rules draft and the seed script both briefly used the renamed fields; both were corrected in the same pass as this decision, before S1-07).
**Consequences:** The product may call it "Site" (construction) in the UI while the schema and code still say "estate"/"supervisor" underneath — that's fine; CONTRACTS C6 only restricts user-facing wording, not internal field names. Construction `estates` reuse `Estate`'s coconut-shaped `area_acres`/`tree_count` fields as rough placeholders (see `scripts/seed.ts`'s comment) since widening the type to a generic `attributes` bag would be the same kind of cross-session change this ADR avoids. If Session 2 later wants a true per-category site-fields schema, that's a CONTRACTS.md change request, not something S1 should pre-empt.

## ADR-014: Supabase replaces Firebase across the whole project (2026-10-04)
**Decision:** Remove Firebase completely. Postgres (Supabase) replaces Firestore, Row Level Security replaces `firestore.rules`/`storage.rules`, Supabase Auth replaces Firebase Auth (phone OTP, staff email/password, Google OAuth for the Drive page), Supabase Storage replaces Firebase Storage, Realtime replaces `onSnapshot`. Server logic is split by what it needs: escrow, awards and memberships are `security definer` Postgres functions called with `supabase.rpc()` (one transaction each, same error codes as the old `HttpsError`s); `create-payment` and `payhere-notify` are Edge Functions, because they need the PayHere merchant secret and a public webhook URL. Hosting moves to Vercel. Started fresh: no Firestore data was migrated.
**Why:** Team decision. Relational data (jobs -> bids -> awards -> payments -> ledger) fits Postgres with foreign keys and transactions better than documents, and RLS removes the Firestore query-shaping rules that caused ADR-008/009/010.
**Consequences:**
- Source of truth: `supabase/migrations/*.sql` (schema, RLS, functions, storage), `supabase/functions/*` (Edge Functions), `src/lib/supabase.ts` (client, `callRpc`, `BackendError`). Column names equal the `src/types` field names (ADR-007 holds), so components did not change.
- Authorization reads `users.memberships` / `users.is_admin` through `private.*` helper functions; there are no custom claims and no token refresh after `add_membership()`.
- Client writes are limited per column with `GRANT UPDATE (cols)`; which party may change what in a bid is a trigger (`private.bids_guard_update`). Money tables have no client write grant at all.
- `confirm_completion()` returns (does not raise) the wrong-PIN error, so its attempt counter is not rolled back. `callRpc` treats both the same.
- The CONTRACTS C2/C3/C4/C5/C7 signatures are unchanged except where noted in CONTRACTS.md (C5 path, C7 error class).
- `VITE_AUTH_MODE=supabase` (was `firebase`) turns on real auth and sync; demo mode and e2e still need no backend.
- Google sign-in for the Drive page uses Supabase's Google provider (team choice over Google Identity Services): it is a redirect, and it replaces the user's phone session. The Google token is kept in memory only (KNOWN_ISSUES #30).
- Tests: `tests/db/` (RLS, functions, storage) run against a real dev project with `npm run test:db`, replacing the emulator suites.
